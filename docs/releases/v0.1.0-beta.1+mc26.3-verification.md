# 0.1.0-beta.1+mc26.3 verification / 検証記録

## Builds and environment

The candidate is the published `0.1.0-alpha.9+mc26.3` runtime for each loader. The physical test server was an i7-7700K. Two participating game clients shared a separate i7-12700K PC. The server and clients used a 32-chunk view distance. The simulation distance was 3. Complete terrain, distinct-peer verification, authoritative biome demand, cooperative NOISE and parallel FEATURES were enabled. The optional native request batching and client request ingress switches were disabled.

## Continuous exploration and restart

The test begins with two players in survival mode. Each mines and places a block, disconnects and reconnects. The server saves and exits. A new server process loads the same world with the same launch arguments and settings. The clients and server check both returning players and the placed blocks before further changes. A second set of survival interactions follows. Both players then explore bounded corridors in creative flight for 60 minutes. The harness samples movement, actual presence of the current chunk in each client's cache, player health and memory every minute. Each owner must show at least ten positive cache samples and fewer than three consecutive misses. Finally both players return to survival, repeat their interactions, save and stop. All three loader rows come from the final run using the corrected client chunk-cache check and the verified approach to the landing area.

After shutdown the readers check the player data, statistics and placed blocks before restart and at the end. They recompute saved lighting from the final blocks for each loader in 50 interior chunks using 162 chunks of surrounding data.

In earlier trials, Fabric completed exploration and saved-world checks in `beta-stability-gate-20261009-162356-447/summary.json`, SHA-256 `75550FF96B2580930E438DAE6560BF30A403C7FB991DA1B20439670409342BC3`. The full October run failed while preparing exploratory flight on Forge.

Forge completed exploration and saved-world checks in `beta-stability-gate-20261110-030617-533/summary.json`, SHA-256 `08885771667CD60BDE3A75B19916226F5FD6C130F79924CE930C026C5A96DEA1`. That run subsequently failed when one NeoForge client returned to survival after the flight. The earlier Fabric and Forge input drivers called a method that always returned true on the client. Packet logs showed earlier receipt for all 240 sampled player/chunk positions across those two runs, but lacked eviction history. Their flags could not establish whether those chunks still occupied the cache. The table above uses the new direct cache observations on all three loaders.

At the end of that flight the controller switched the players to survival and teleported them to their distant starting positions. One NeoForge player reported full health and feet at Y70, one block below the expected Y71. The survival-mode notification preceded receipt of both landing chunks on the same client by 401 ms. Offline reading of the stopped server's FULL chunks found the original full grass block at Y70 and clear space at Y71 before and after the failed landing. The neighboring placed cobblestone also persisted. The final region file has SHA-256 `BEF8546B3E6AF44DF58286CCB5320CB9A44BE90BA4E71C5103963944C2EA2451`.

The revised test places both players over their original landing areas while still in creative flight. It requires the stand and target chunks to be present in each client's cache, the original solid dry floor, clear space above it and the previously placed cobblestone. The server checks the corresponding locations and the hovering players before switching them to survival. The players then have to land at the exact expected height. Abrupt survival teleports before chunk receipt remain an open case. Beta.1 ships the alpha.9 generation code and makes no general fix for that case.

## Earlier measurements

The six matched Fabric dev.23 assistance OFF/ON comparisons reused three regions in both execution orders. Median FULL time fell 20.93%, required client receipt time fell 21.20%, and server CPU time fell 19.63%. Tick p95 rose 8.95%. All six paired FULL times improved. Source: `authoritative-biome-confirmation-20261007-003107-976/summary.json` and its identified first-order run. These figures compare two settings of the same installed mod. A separate correctness fixture for each of the three loaders matched 882 coordinates for NOISE, decoration, saved structures and saved lighting. The earlier alpha.9 verification documents the archive comparisons linking that evidence to the active generation code.

Forge and NeoForge also have a separate, earlier comparison of optional client request ingress with assistance enabled in both conditions. Median FULL time changed by −2.92% on Forge and −0.20% on NeoForge. Forge server CPU time rose 9.99%. These measurements concern the optional native switch. Both native switches default to off.

## 日本語

距離32、弱い専用サーバー1台、別PC上の参加クライアント2人という条件で検証しました。3ローダーすべてで、クライアントのチャンクキャッシュを直接確認し、着地地点を受信してからサバイバルに戻す手順で再検証しました。 過去のFabric・Forgeでは各60分の探索と保存確認が完了していましたが、当時の判定は常に真を返し、計測時点でチャンクがキャッシュに残っていたかは確認できませんでした。

11月10日の先行試験では、NeoForgeで管理用コマンドが飛行中のプレイヤーをサバイバルに切り替えて遠方の出発地点へ戻したとき、1人が体力20のまま本来より1ブロック低い着地を報告しました。保存ワールドには元の草ブロックと隣に置いた丸石が残っていました。そのクライアントではサバイバルへの切替通知から着地地点の2チャンクを受信するまでに約0.4秒の間隔がありました。

再検証では両クライアントが着地地点を受信した後にサバイバルへ戻し、元の高さで着地することを求めます。受信を待たずサバイバルで遠距離転送した場合の問題は未解決です。配布版にはこの操作に対する一般的な修正を加えていません。3ローダーでそれぞれ、60回の1分間隔サンプル、4件の保存済みプレイヤーデータ、10,649,600個の照明値を確認しました。3種類の配布JARはいずれも、試験済みのalpha.9とローダーの版情報だけが異なり、ソースJAR内の各ファイルも一致しました。

速度の数値は過去のFabric支援ON/OFF比較です。実行順を入れ替えた6組では、生成完了時間が中央値20.93%短くなり、遅い側のサーバーtickは8.95%長くなりました。今回の探索で重視しているのは、実際の支援が続く環境で移動・再接続・再起動を行い、その結果がワールドに正しく残ることです。
